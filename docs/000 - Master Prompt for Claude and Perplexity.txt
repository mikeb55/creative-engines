1. GCE v2.0 — Grand Criteria of Excellence (musical quality score)
────────────────────────────────────────
What: 10 categories, each 0–10, weighted into overall score.
Categories: cadential clarity · melodic identity · phrase grammar · harmony & language · rhythmic identity · structure & form · arrangement & orchestration · economy & focus · tension & release · thematic recall potential.
Formulas/weights/thresholds: docs/GCE_FRAMEWORK_V2.md only.

Calibrated bands (guidance — formulas unchanged):
- 9.0 = aspirational north star (long-term benchmark)
- 7.9–8.4 = current empirical release-quality / system-ceiling band
- ≥7.9 = operational PASS for tuned shipped output
- 6.5–7.8 = acceptable; one DCR pass on weakest category
- <6.5 = materially weak; investigate

GCE HARD GATES (auto-fail regardless of overall score):
- Melodic identity ≤ 6
- No section contrast
- Cadential clarity coverage < 0.4
- Final bar tension > 0.7 — CONTEXT-AWARE as of endingContext fix (2026-07-23):
    - endingContext = 'terminal' (Song Mode, leadsheets, standalone final charts): gate unchanged, still fails at >0.7 (unresolved ending = genuine flaw)
    - endingContext = 'loop' (riff_generator default — riffs are built to cycle back to bar 1): gate does NOT auto-fail on tension >0.7; unresolved/tense endings are expected and often correct for a loop
    - endingContext = 'open_idiom' (intentional unresolved terminal ending): requires explicit user acknowledgment/disclosure (chord-loop-trust-style), not a silent pass or fail
    - Threshold itself (0.7) is unchanged — only which contexts trigger the hard-fail changed

Short-form caveat (< ~16 bars, especially 8-bar leadsheets):
Some categories are structurally limited (thematic recall, structure & form, parts of phrase grammar). Still meaningful: rhythm anti-loop, harmony/chord fidelity, range/idiomaticity, hard gates.

TWO AGENT MODES (same math; different application):
| Mode | When | Behaviour |
| Formal / technical | Code changes, evaluator runs, LOCK/DCR/CI, release readiness, automated harness scores | Hard gates block; operational band applies; DCR one pass on weakest category |
| Musician-facing / conversational | Chat: "GCE this", "is this good?", "pros and cons?" | Musical critique on 0–10 scale; NOT repo PASS/FAIL unless user explicitly asks for formal validation or mentions LOCK/DCR/CI |

Chat output shape (musician-facing): overall score · 2–4 strengths · 2–4 weaknesses · one highest-leverage improvement · tag as musical refinement / technical fix / architectural concern.

────────────────────────────────────────
2. LOCK — pre-commit compliance (merge blockers)
────────────────────────────────────────
LOCK hard gates are the real merge blockers. Calibrated GCE band is guidance; it does not override LOCK or GCE hard gates.

L — Locked truth: harmony bars / slice precompute / effective harmony must match export XML and getChordForBar routing; no drift between UI symbols, engine bars, and MusicXML.
O — Output integrity: export/readiness gates pass (exportIntegrityPassed receipt, schema-safe XML, shareable output paths).
C — Category hard fails: no GCE hard gate violations on representative output.
K — Key verification: engine/smoke changes → npm run test:composer-smoke; slice/docs → design-time GCE checklist on representative seeds.

Runtime receipts on Generate: behaviourGatesPassed, exportIntegrityPassed (see behaviourGates.ts, composerOsAppGeneration.ts).

────────────────────────────────────────
3. DCR — build workflow (Design · Commit · Refine)
────────────────────────────────────────
Not "DPR" — the repo term is DCR.
D — Design: goal, scope, GCE targets, Style Profile Layer, LOCK acceptance checks.
C — Commit: implement deterministically; ship docs/changelog/playbook with user-facing changes.
R — Refine: ONE pass on weakest GCE category OR single blocking LOCK item. No full rewrite. No infinite tweak loops. If still failing after one Refine → return to Design.

On short-form: skip blind refine of structurally limited categories; re-score on full chart (≤64 bars) first.

────────────────────────────────────────
4. Style Profile Layer — per-composer monitoring
────────────────────────────────────────
Every composer slice (SongwriterRuleId) and relevant StyleProfile must define:
- Primary GCE categories to monitor for that voice
- Engine hooks (harmony precompute, melody profile, style engine)
- Diagnostics (receipt prefixes: ec:*, fz:*, ba:*, etc.)
- Eval entry points: slice smoke tests, npm run eval:<name>

HOW AGENTS ACTUALLY RUN SCORES (code, not guesswork)
────────────────────────────────────────
Automated GCE implementation lives under engines/composer-os-v2/core/gce/ and core/evaluation/:
- gceEvaluator.ts, gceAutoScorers.ts, lockGates.ts, featureExtractor.ts
- behaviourGates.ts — pipeline behaviour + LOCK suite at generation time
- leadSheetGceLockEvalRunner.ts — leadsheet quintet path: evaluateGce + evaluateLock
- endingContext.ts + finalBarTensionGate.ts — context-aware final bar tension gate (terminal/loop/open_idiom)

CLI / npm entry points:
- npm run eval:gce-styles — cross-preset style sweep (engines/composer-os-v2/scripts/gceStyleEval.ts)
- npm run eval:<composer> — per-slice harness (eval:brian_wilson, eval:fagen, eval:bacharach, eval:ecm-texture, etc.)
- npm run test:composer-smoke — aggregate smoke tier (~489 PASS rows / 94 suites full; sync CLAUDE.md + roadmap when allowlist changes)
- Leadsheet proof CLIs: runLeadSheetOrbitGceLockProofCli.ts, runDebussyLeadSheetInputProofCli.ts, etc.

Typical agent workflow for formal validation:
1. Read docs/GCE_CANONICAL.md + docs/GCE_LOCK_DCR_STANDARDS.md
2. Generate or load representative MusicXML/score for the touched path
3. Run official evaluator script or smoke test for that slice
4. Report: overall GCE, weakest category, hard gate PASS/FAIL, LOCK receipts (including endingContext for finalBarTension)
5. If below band: one DCR refine on weakest craft category only

Typical agent workflow for chat critique:
1. Default musician-facing mode unless user says LOCK/DCR/CI/formal validation
2. Apply GCE vocabulary musically; mark short-form structural limits
3. Do not auto-fail sub-9 scores or recommend architecture rewrites from one low score
4. For riff/loop-oriented output, do not flag an unresolved final bar as a flaw — that's expected loop-closure behavior, not a weakness
